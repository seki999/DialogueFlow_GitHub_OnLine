# Secrets 管理：为什么不能直接写密码

理解为什么明文密码会泄漏，以及更安全的 Secrets 处理方式。

```mermaid
flowchart LR
    A[OCI Vault] --> B[Secret]
    B --> C[OpenTofu 只保存 Secret OCID]
    C --> D[应用运行时读取 Secret]
```

## 核心要点

* 错误写法：variable 直接 default 明文密码，会进入 Git 历史、Plan 文件、State 文件、CI 日志
* 较好的方式：密码存入 OCI Vault，OpenTofu 只保存 Secret OCID，应用运行时读取 Secret
* 也可以由 CI 通过 TF_VAR_ 前缀环境变量注入，但密码仍可能进入 State，取决于资源属性和 Provider 行为
* sensitive = true 不是加密，只是隐藏部分界面输出

## 本章测验

本章共 5 道单项选择题。

### 第 1 题

为什么不建议直接在 variable 的 default 中写明文密码？

- A. 因为 OpenTofu 不支持字符串类型
- B. 因为这样写会导致语法错误
- C. 因为它会进入 Git 历史、Plan 文件、State 文件、CI 日志
- D. 因为密码长度受限

<details>
<summary>选择答案后查看结果</summary>

正确答案：C

答案解析：文中明确指出明文密码写在 default 中会进入 Git 历史、Plan 文件、State 文件、CI 日志，造成多处泄漏风险。

</details>

### 第 2 题

文中推荐的较好的密码管理方式是什么？

- A. 把密码写在 README 里方便查阅
- B. 把密码打印在终端方便调试
- C. 把密码写死在 Provider 配置里
- D. 密码存入 OCI Vault，OpenTofu 只保存 Secret OCID

<details>
<summary>选择答案后查看结果</summary>

正确答案：D

答案解析：文中给出的流程是密码存入 OCI Vault 生成 Secret，OpenTofu 只保存 Secret OCID，应用运行时再去读取真正的 Secret 内容。

</details>

### 第 3 题

通过 TF_VAR_ 环境变量注入密码后，是否绝对不会进入 State？

- A. 仍可能进入 State，取决于资源属性和 Provider 行为
- B. 绝对不会，环境变量注入完全安全
- C. 只要设置 sensitive = true 就绝对不会进入 State
- D. 只有在生产环境才会进入 State

<details>
<summary>选择答案后查看结果</summary>

正确答案：A

答案解析：文中明确提醒即使通过 CI 用 TF_VAR_ 注入，密码仍可能进入 State，这取决于具体资源属性和 Provider 的实现行为。

</details>

### 第 4 题

sensitive = true 的实际作用是什么？

- A. 对数据进行加密存储
- B. 只是隐藏部分界面输出，不是加密
- C. 彻底阻止数据写入 State
- D. 自动轮换密码

<details>
<summary>选择答案后查看结果</summary>

正确答案：B

答案解析：文中强调 sensitive = true 不是加密，只是隐藏部分界面输出，不能替代真正的 Secrets 管理机制。

</details>

### 第 5 题

下列哪一项不是文中提到的明文密码可能泄漏的位置？

- A. Git 历史
- B. Plan 文件
- C. 浏览器书签
- D. CI 日志

<details>
<summary>选择答案后查看结果</summary>

正确答案：C

答案解析：文中列出的泄漏位置是 Git 历史、Plan 文件、State 文件、CI 日志，并未提到浏览器书签。

</details>
