# 实验步骤：Terraform 在已有 OKE 部署 Nginx

## 先确认实验范围

主实验不创建 VCN、OKE、Node Pool 或真实数据库。它只创建新的 tf-oke-learn Namespace、网页 ConfigMap、Deployment 和 Service；Kubernetes 派生 ReplicaSet 与 Pod。需要已有可用 OKE 与工作节点、Terraform、kubectl、OCI CLI、有效客户端认证及 API 网络路径。不要把独立 VCN 示例当成集群创建工程。

以下命令在 PowerShell 执行。路径、Region、OCID 和 Context 必须替换为自己的值。命令步骤供使用者复现，本次制作未执行任何真实集群或云变更。

## 1. 客户端配置与目标检查

若已有单独 kubeconfig，直接使用；需要新生成时，先选择自己的输出路径，父目录须存在，且不要覆盖要保留的配置：

```powershell
oci ce cluster create-kubeconfig --cluster-id REPLACE_CLUSTER_OCID --file "C:/ACTUAL_PATH/oke-learning.config" --region REPLACE_REGION --token-version 2.0.0 --kube-endpoint PRIVATE_ENDPOINT
```

PRIVATE_ENDPOINT 要求当前执行环境有适当私有网络路径；公开访问只有实际提供公开 API 时才用 PUBLIC_ENDPOINT。OCI CLI 认证、集群访问权限和网络需分别满足。认证通过 kubeconfig 的 exec 机制可能依赖可执行的 OCI CLI。

设置本次 shell 的任务变量，不修改系统 HOME 或 CODEX_HOME：

```powershell
$OkeCourseConfig = "C:/ACTUAL_PATH/oke-learning.config"
kubectl --kubeconfig $OkeCourseConfig config get-contexts
$OkeCourseContext = "REPLACE_WITH_ACTUAL_CONTEXT"
kubectl --kubeconfig $OkeCourseConfig --context $OkeCourseContext get nodes
```

检查点：目标是自己的学习集群，能看到具备运行条件的 Node。API 查询成功不保证业务公网入口或存储都可用。

## 2. 准备完整应用工程

从本课中文版目录进入应用工程：

```powershell
Set-Location "terraform/oke-nginx"
Copy-Item -LiteralPath "terraform.tfvars.example" -Destination "terraform.tfvars"
```

编辑 terraform.tfvars，把 kubeconfig_path 和 kubeconfig_context 分别设为前面实际值。Windows 路径用正斜杠。确认 namespace 是新的、专用于自己实验的名字，默认 tf-oke-learn；如果它已经存在，不要不加判断地让示例接管或删除它。

主线保留 replicas=2、image=nginx:1.28、service_type=ClusterIP。两个 Provider 示例目录各是独立工程，不合并 State。

## 3. 初始化、校验、审阅与应用

```powershell
terraform init
terraform fmt -check
terraform validate
terraform plan -out=review.tfplan
terraform apply review.tfplan
```

检查点：计划应直接创建 Namespace、ConfigMap、Deployment、Service 四个资源，不应创建 VCN、OKE 或 Node Pool。若计划出现不属于本实验的对象，先核对目录、变量、State 和目标集群。计划文件与 State 可能包含敏感信息，不公开提交。

validate 只检查配置，plan 会连接实际 API，apply 执行实际变更；三者不能当成同一件事。完整实验的 Provider 版本约束在 versions.tf，init 产生锁文件可按自己的工程流程保存。

## 4. 观察派生资源与就绪

下面沿用前面的 PowerShell 变量；若使用新终端，应重新设置它们。若修改 namespace，应替换对应值。

```powershell
kubectl --kubeconfig $OkeCourseConfig --context $OkeCourseContext get deployment,rs,pods,service,configmap -n tf-oke-learn
kubectl --kubeconfig $OkeCourseConfig --context $OkeCourseContext rollout status deployment/oke-nginx -n tf-oke-learn
kubectl --kubeconfig $OkeCourseConfig --context $OkeCourseContext get endpointslices -n tf-oke-learn -l kubernetes.io/service-name=oke-nginx
```

检查点：期望两个就绪 Nginx Pod，模板和 Service 使用 app=oke-nginx，ConfigMap 的网页挂载到 /usr/share/nginx/html。ReplicaSet 与 Pod 由控制器创建，未单独作为 Terraform resources。

## 5. 本地访问

```powershell
kubectl --kubeconfig $OkeCourseConfig --context $OkeCourseContext port-forward service/oke-nginx 8080:80 -n tf-oke-learn
```

保持终端运行，浏览器访问 http://localhost:8080，预期看到“Terraform + OCI OKE + Kubernetes”及来自 ConfigMap 的课程网页。若被转发的 Pod 替换，可能需要重启通道。此方式不是永久公网入口，也不能证明所有 Service 转发或外部云入口路径都已测试。

## 6. 可选副本调整

把 terraform.tfvars 的 replicas 改为 3，再重新 plan 和 apply。观察 Pod 数量变化，不把它等同于三台 Compute。长期配置在 Terraform 中维护，kubectl 用于查询和日志；不要用手工修改覆盖同一声明来源。

## 7. 可选 OCI LB 扩展

只有明确要验证云入口，且已了解自己的云资源成本与网络条件时，才修改同一工程变量：

```hcl
service_type = "LoadBalancer"
lb_type      = "lb"
```

再次 plan、审阅和 apply 后，观察 Service 状态与 OCI LB：

```powershell
kubectl --kubeconfig $OkeCourseConfig --context $OkeCourseContext get service oke-nginx -n tf-oke-learn -w
```

等待并检查实际入口。它可能是私有入口，后端路径取决于 CNI 与实现；没有出现地址时不能伪称实验成功。OCI LB 由云集成供给，不是本工程的显式 OCI resource。NLB 可将 lb_type 改为 nlb，但应核对相应条件，本课不会替你安装或补全云网络。

## 8. 清理自己的应用实验

Ctrl+C 停止 port-forward。确认此 Namespace 没有放入其他需要保留的对象，再审阅删除计划：

```powershell
terraform plan -destroy -out=cleanup.tfplan
# 确认是自己的应用工程与实验范围之后，才执行：
terraform apply cleanup.tfplan
```

Namespace 删除可能包含后来创建的对象。若做了 LB 扩展，要在 OCI 中确认关联 LB 的清理；State 直接列表不等于全部间接影响。本应用工程不直接管理原有 OKE、Node Pool 与 VCN，不能在基础设施工程目录照抄此清理。

## 独立 VCN 示例如何使用

terraform/oci-vcn 有自己的版本、Provider、变量、资源和输出。使用者先配置本机 DEFAULT APIKey profile，将 terraform.tfvars.example 复制为 terraform.tfvars 并填实际 Compartment，再 init、validate、plan，审阅后才 apply。输出 vcn_ocid 只代表 VCN 标识，没有 Subnet、Gateway、OKE 或 Node Pool。

## 条件性 YAML 的使用说明

examples/ 各文件是独立主题，不整目录应用。它们使用 oke-cloud-examples Namespace，须先建立自己的实验空间。LB 示例还需 app=standalone-web 后端与云网络；Ingress 还需真实类、Controller、后端和解析；OCIR 示例还需实际镜像与同空间拉取 Secret；PVC 示例还需实际 oci-bv 类和供给能力。存储消费者不运行真实数据库，定时任务只输出文本。
